Java · async memory map — part 3

Compose & errors
by signature.

Four methods, four different functional interfaces. The shape of the lambda you pass tells you exactly what each one can do — and whether it can recover, transform, or only watch.

The signatures
thenComposeflatMap · sequence a dependent async call
Function<T, CompletableFuture<U>> → CompletableFuture<U>
fires on success returns CF<U> transforms yes

Your lambda returns another future. Compose flattens CF<CF<U>> into CF<U>. Use when step B depends on step A's result and is itself async.

exceptionallyrecover · failure only
Function<Throwable, T> → CompletableFuture<T>
fires on failure returns CF<T> (same T) recovers yes

Only runs if upstream failed. On success the value passes straight through untouched. Can't change the type — the fallback must be the same T.

handleboth paths · most powerful
BiFunction<T, Throwable, U> → CompletableFuture<U>
fires on both returns CF<U> recovers yes

Always runs. Exactly one argument is non-null — value on success, throwable on failure. Can recover and change the type. The Swiss-army knife.

whenCompleteobserve · side-effect only
BiConsumer<T, Throwable> → CompletableFuture<T>
fires on both returns CF<T> (passthrough) recovers no

A Consumer, not a Function — returns nothing. The original value (or exception) propagates unchanged. For logging, metrics, cleanup. Cannot swallow the error.

The three error handlers, side by side
methodfires oncan recover?changes type?returns
exceptionally failure only yes no (same T) CF<T>
handle success + failure yes yes (→ U) CF<U>
whenComplete success + failure no no (passthrough) CF<T>

Mnemonic: Function recovers, Consumer only watches. exceptionally & handle take a Function → they return a new value, so they can swallow the error. whenComplete takes a Consumer → it returns nothing, so the original outcome flows on.

Async variants: all four have ...Async(fn, executor) — pass a virtual-thread executor for I/O-bound recovery.
Bonus (Java 12+): exceptionallyCompose = recover by returning another future (e.g. retry a fallback service) — like exceptionally but flatMapped, the way thenCompose relates to thenApply.
Gotcha: the Throwable is usually wrapped in CompletionException — unwrap with getCause() before matching on type.
