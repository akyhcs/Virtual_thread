Virtual vs Platform threads

Virtual

JVM-managed · cheap · millions
  • Best for I/O-bound: network, DB, file calls
  • Parks for free when blocked — frees the OS carrier thread
  • High concurrency: 10k+ in-flight requests, no tuning
  • Create one per task — never pool them
  • No speedup for pure CPU work

Platform

1:1 OS thread · ~1MB · thousands
  • Best for CPU-bound: parsing, encoding, math
  • Use a bounded pool sized ≈ CPU cores
  • Needed for thread-affinity / native-bound work
  • Expensive to create — so you pool & reuse them
  • Blocking one wastes a whole OS thread

So which is best?

Neither universally — it's the workload, not the thread, that decides. But for typical Spring Boot service work — which is mostly waiting on I/O — virtual threads are the default win: same simple blocking code, far higher throughput, no pool to size.

Reach for a bounded platform pool only when a stage is genuinely CPU-bound, or you must cap parallelism against a fragile downstream (e.g. a DB with few connections).

Pinning, historically: a virtual thread used to "pin" its carrier inside a synchronized block or native call, blocking other virtual threads. Fixed in JDK 24 (JEP 491) — synchronized no longer pins. On older runtimes, prefer ReentrantLock on hot paths.
Also: avoid heavy ThreadLocal with millions of virtual threads · don't pool virtual threads · default since Java 21.
